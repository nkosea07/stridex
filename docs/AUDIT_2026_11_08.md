# Code and Flow Audit (2026-11-08)

Audit of the committed implementation (`c91af3f`) against the documentation in `docs/`, the
per-app READMEs, and `AGENTS.md`, looking for inconsistencies, bugs, and defective flows. Every
finding below was fixed in the same change set; verification evidence is at the end.

## Timing and results

| # | Severity | Finding | Fix |
|---|---|---|---|
| T1 | High | Timing start was `checked_in_at`, else `registered_at`. Check-in is the desk/QR check-in that happens at bib pickup, so chip times, splits, live elapsed time, ETA, insights, and cutoffs were measured from the day before the race (or registration). With a cutoff configured, every participant without a START mat read was marked DNF at the first cutoff checkpoint. | One definition in `CheckpointCutoff.resolveStart`: earliest START record, else the scheduled gun start (`raceDate` + `startTime` in the race timezone). Applied to results (Java and the ranking SQL), cutoffs, live tracking, public tracking, and insights. Gun time is now measured from the scheduled start instead of duplicating chip time. |
| T2 | High | Staff manual/QR records and CSV timing imports never advanced participant status (no STARTED/FINISHED, no follower alerts). Results only rank `FINISHED` participants, and race completion turns `STARTED` into `DNF`, so a volunteer-timed finish produced no result and an RFID start plus manual finish became DNF. | `CheckpointProgression` applies one status transition and alert policy for RFID, staff, import, and athlete paths. |
| T3 | High | RFID and athlete FINISH reads overwrote `DISQUALIFIED`/`DNF`/`DNS` with `FINISHED`; RFID sent a "started" alert on every intermediate checkpoint. | Official/terminal states are never overwritten by a read; start/finish alerts fire only on an actual transition. |
| T4 | High | The athlete self-scan route accepted a client-supplied timestamp, so an athlete could set their own official finish time. The staff route already rejects client timestamps. | Server receipt time is used; client timestamps are ignored. |
| T5 | Medium | Race `timezone` was stored without validation. | Create/update reject non-IANA zones (`INVALID_TIMEZONE`); readers fall back to UTC for legacy bad values, and the SQL joins `pg_timezone_names`. |

## GPS tracking

| # | Severity | Finding | Fix |
|---|---|---|---|
| G1 | High | The drift filter compared each point with the latest stored point, including rejected ones. One bad fix (low accuracy, spike) caused the next good point to be rejected as implausible speed and distance to accumulate from a bogus position. | Comparison uses the latest accepted point (`findTop...AndFilteredFalse...`). |
| G2 | Medium | Rejected points were broadcast on the live WebSocket and could be returned as a participant's "latest" position on staff and public feeds. | Only accepted points are broadcast or used as latest. |
| G3 | Medium | The public (anonymous) heatmap included participants who disabled tracking and accepted 6-decimal (≈0.1 m) cells. | Tracking-disabled participants are excluded; public precision is capped at 4 decimals. |
| G4 | Low | GPS batch ingest had no size limit. | `@Size(max = 500)` (mobile sends at most 100). |
| G5 | Medium | Mobile could run two uploads of the same pending rows concurrently (location task and background sync task). | Per-race in-flight guard in `syncPendingLocations`. |
| G6 | Medium | The mobile QR scanner showed "Checkpoint Recorded!" before the request and swallowed failures. | The scanner awaits the server and reports failure; strings moved to `mobile:scanner`. |

## Authentication and sessions

| # | Severity | Finding | Fix |
|---|---|---|---|
| A1 | High | `login` is transactional; failed-attempt counters and lockout were written and then rolled back by the `UnauthorizedException`, so account lockout never took effect. | `@Transactional(noRollbackFor = UnauthorizedException.class)`. |
| A2 | High | Every login, refresh, and OAuth sign-in revoked all of the user's other refresh tokens, so signing in on the web logged the phone out (stopping background GPS upload) and each device's refresh logged out the other. | Sessions rotate only the presented token; password reset and account deletion still revoke all sessions. |
| A3 | High | Web live map and alert sockets captured the access token once. After a reload (token `null` until refresh) or token expiry, every reconnect re-sent the stale token and was rejected indefinitely. The cleanup closure also disconnected whichever client was in a shared module variable. | Token is resolved (and refreshed if near expiry) in `beforeConnect` on every attempt; each subscription owns and disconnects its own client. |

## Payments

| # | Severity | Finding | Fix |
|---|---|---|---|
| P1 | High | Checkout could start for an already `PAID` (or `WAIVED`) registration, charging twice. | Rejected with `PAYMENT_ALREADY_COMPLETED` / `PAYMENT_WAIVED`. |

## RFID pipeline

| # | Severity | Finding | Fix |
|---|---|---|---|
| R1 | High | Gateway: a network error or timeout during flush left the leased batch in `processing/` until restart. | Batch is returned to `pending/` with backoff. |
| R2 | High | Gateway: a batch the backend rejects permanently (e.g. 400 for simulated reads against production) was requeued forever and, being first in order, blocked every later read. | Permanent 4xx batches move to `failed/`; health exposes `failedFiles`; `POST /failed/requeue` replays them. |
| R3 | Medium | Gateway: heartbeat network errors bypassed failure counting/backoff, and one heartbeat failure left the gateway reporting `DEGRADED` until a read was flushed. | Separate flush/heartbeat error state, counted and cleared independently. |
| R4 | Medium | Gateway: `RFID_GATEWAY_BATCH_SIZE=0` looped forever; values above 200 were always rejected by the backend; malformed `readAt`/`rssi` were spooled and later rejected. | Bounded config; reads validated at `POST /reads`; internal errors return 500, validation 400. |
| R5 | Medium | Backend published stream entries before the ingest transaction committed (worker could ack before the row existed; a rollback published phantom IDs). | Publish after commit. |
| R6 | Low | Re-sending a batch to a revoked reader hit the `(reader_id, source_event_id)` unique index (HTTP 500) instead of reporting duplicates. | Duplicate check runs before the revoked-reader path. |

## Follow-up fixes (design decisions taken)

| # | Finding | Decision and fix |
|---|---|---|
| F1 | Races were auto-closed (and running participants marked DNF) when the server's calendar date passed, so a race crossing midnight was closed mid-race; multi-day stages and race timezones were ignored. | `RaceClosePolicy`: close at the latest scheduled start (race or last stage) + course time limit (longest checkpoint cutoff, else `RACE_DEFAULT_TIME_LIMIT_HOURS`, default 24) + `RACE_COMPLETION_GRACE_MINUTES` (default 60), in the race timezone. Unknown start time ⇒ never before the local day ends. |
| F2 | Mobile retried a permanently rejected GPS batch forever, blocking newer points; uploads for a race the athlete could no longer track never stopped. | Failures are classified: retry (network/429/5xx), reject (400/413/422 → `synced = 2`), or stop (403/404 → also stops tracking, persists the reason, one-time alert). |
| F3 | Two concurrent refreshes with the same token could both succeed, and reuse of a rotated token went unnoticed. | V43 adds `auth_tokens.family_id` (per device session). Refresh consumes the token with a conditional `UPDATE` (only one winner). Reuse within 30 s is a benign race (plain 401; the web client retries once when another tab already rotated the session); later reuse revokes that family only and is audited (`REFRESH_TOKEN_REUSE`). |
| F4 | Login returned `EMAIL_VERIFICATION_REQUIRED` before checking the password, revealing unverified accounts. | The verification message is returned only after the password matches; a wrong password is a generic, counted failed login. Registration's "Email already exists" response is unchanged by decision (rate limited). |

## Remaining smaller issues (fixed)

| # | Finding | Fix |
|---|---|---|
| S1 | Correcting a checkpoint time never re-evaluated cutoffs or status. | All of the participant's cutoff flags are recomputed from the corrected start; a new miss ⇒ DNF, a reversed cutoff-only DNF ⇒ STARTED/FINISHED. |
| S2 | Waitlisted, pending-approval, and rejected registrations could be timed. | Staff, import, and athlete paths return `PARTICIPANT_NOT_ENTERED`; RFID marks the event `ERROR`. |
| S3 | A failing RFID event was republished every 5 s forever and the 100-event recovery window could starve newer reads. | V44 adds `processing_attempts`/`next_attempt_at`; failures back off (5 s → 5 min) and become `ERROR` after 8 attempts; recovery skips backing-off and just-ingested events. |
| S4 | Checkout called Pesepay inside the database transaction; provider exception text was returned to clients. | Stage → provider call (no transaction) → record; failures mark the payment `FAILED` and return `PAYMENT_PROVIDER_UNAVAILABLE` with details only in logs. |
| S5 | Compose defaulted to an unverified sandbox Pesepay URL; `.env.pilot.example` used the live one. | Compose uses `https://api.pesepay.com/api/payments-engine/v1`; production rejects sandbox/non-HTTPS URLs and missing keys when payments are enabled. |
| S6 | Kubernetes preflight did not require `REDIS_PASSWORD` (Compose does). | Required by preflight and documented in `deploy/k8s/config.yaml`. |
| S7 | Uploaded and rejected GPS points were never deleted on the device. | Pruned after 7 days outside active sessions; unsent points are kept. |
| S8 | `DEVELOPMENT_GUIDE.md` listed wrong ports, a `/ws` socket, `DATABASE_URL`/`REDIS_URL`, and a committed `JWT_SECRET` value. | Operational sections rewritten; design-prompt sections marked historical; the secret removed (it remains in git history — rotate it anywhere it was used). |
